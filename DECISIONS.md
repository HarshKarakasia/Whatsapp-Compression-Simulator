# Decisions

## Phase 0 — Harsh's WhatsApp Compression Simulator

- **Tested on:** 2026-10-17, using the synthetic `test_input.mp4` from Phase 0 (ffmpeg `testsrc` + `sine`, 320x240, 15fps, 3s, no real footage).
- **Repo:** `https://github.com/HarshKarakasia/Whatsapp-Compression-Simulator`, cloned into `external/whatsapp-compression-simulator/`.
- **Scriptable, no GUI:** confirmed. `compress.py` is a pure CLI (`argparse`), video-in/video-out, with `--dry-run`, `--batch`, and single-file modes. No GUI dependency. Detects `ffmpeg`/`ffprobe` via `shutil.which()` first (Windows registry paths are a fallback only), so it works unmodified on macOS once ffmpeg is on `PATH`.
- **Exposes real parameters, not a black box:** confirmed. Every run writes a JSON sidecar (`output/simulated/<stem>_simulated.json`) containing the exact encoder (`libx264`), CRF (28), preset (`medium`), pixel format (`yuv420p`), max resolution box (1280x720), audio codec/bitrate, the full `ffmpeg` argv list, and the exact command string. Ran `--dry-run` first to preview the command, then a real run — both matched exactly.
- **Runs cleanly, no manual intervention:** confirmed. `python3 compress.py input/test_input.mp4` succeeded in 0.09s on the first try, output file is a valid playable MP4 (`ffprobe` confirms `h264`/`aac` streams).
- **Decision: integrate it as the "WhatsApp hop" implementation inside `src/pipeline/`** (wrap, don't fork-and-edit). Its CLI contract (`compress.py <input> [--crf --max-width --max-height --preset --fps]`, JSON sidecar with `parameters` + `ffmpeg_command_args`) is stable enough to shell out to directly, and its sidecar's `parameters`/`ffmpeg_command_args` double as the actual-vs-requested metadata Phase 2 needs anyway. `compare.py`'s ffprobe-based metadata/comparison pipeline will **not** be reused — Phase 2 already specs its own `src/pipeline/probe.py`, and duplicating that logic would just be two sources of truth for the same ffprobe fields.
- **Caveat:** the simulator's baseline profile (CRF 28, max 1280x720, `medium` preset) is a *single* fixed recipe calibrated for one WhatsApp hop. Phase 1's multi-codec, multi-generation chain (H.264/H.265/VP9/AV1 × 3 depths, per `configs/transform.yaml`) needs its own recipe table regardless — this simulator covers one point in that space (H.264 generation-1-ish), not the whole tree. It will be wrapped as one named recipe/codec option, not treated as the full Phase 1 pipeline.

## Phase 0 — ffmpeg toolchain

- **Tested on:** 2026-10-17.
- **Problem:** `brew install ffmpeg` on this machine could not fetch pre-built bottles (bottle host unreachable in this sandboxed environment) and fell back to compiling ffmpeg + all codec deps (x264, x265, aom, dav1d, svt-av1, ninja as a build-tool dependency) from source. Verified via `ps aux` mid-install: it was still building `ninja` itself ~5 minutes in, before even reaching `x265`/`ffmpeg`. Estimated 15-20+ minutes remaining.
- **Decision:** killed the brew build. Used a dedicated conda-forge environment instead (`conda create -n fyp-ffmpeg -c conda-forge ffmpeg`), which installed in under a minute and provided ffmpeg 9.0.2 with the full codec set this project needs: `libx264`, `libx265`, `libvpx-vp9`, `libsvtav1`.
- **Caveat:** the base conda environment's `ffmpeg` (an older, codec-incomplete 4.3.2 build pulled in as a side effect of testing conda-forge) sits earlier on `$PATH` than both Homebrew and the new env, and `conda remove` refused to uninstall it cleanly (unrelated `requests`-is-a-conda-dependency conflict). Rather than fight global `$PATH` order or force-remove conda package files, `configs/paths.yaml` pins the correct binaries by absolute path (`ffmpeg_binary` / `ffprobe_binary`), and all project code must resolve ffmpeg through that config value, not through `$PATH` lookup. This is also just more reproducible than relying on shell PATH order across machines.

## Phase 1 — Transform chain scaling filter and rate control

- **Scaling:** all four codecs use the same "max box, never upscale, preserve aspect, even dims" scale filter as Harsh's simulator (`scale=w='min(iw,W)':h='min(ih,H)':force_original_aspect_ratio=decrease,...`), rather than forcing an exact target height. On the tiny 320x240 synthetic clip this means resolution stays unchanged through the whole chain (it's already below every hop's box) — expected and fine for a synthetic mechanics test; on real FF++/Celeb-DF source footage (720p+) this will actually downscale through the ladder as the spec intends.
- **Rate control bug found and fixed:** `libsvtav1` rejects `-maxrate`/`-bufsize` outside CRF mode (`Max Bitrate only supported with CRF mode`), which broke every AV1 hop whose input was itself a prior generation. Fixed via a per-codec `supports_maxrate_bufsize` flag in `configs/transform.yaml` — AV1 gets `-b:v` alone (VBR target, no hard ceiling); h264/h265/vp9 keep the tight VBV cap (`-maxrate`/`-bufsize` = target bitrate).
- **Audio:** the whatsapp-simulator-wrapped h264 hop keeps AAC audio (no CLI flag to disable it short of the source having none); the three direct-ffmpeg hops (h265/vp9/av1) drop audio via `-an` for simplicity and because muxing video-only VP9/AV1 into `.mp4` is more reliably supported than audio+VP9/AV1 combinations across ffmpeg builds. This means audio presence varies by lineage — harmless for Phase 1's mechanical tests, worth knowing before Phase 4 preprocessing (which only reads video frames anyway).
- **Encoder speed:** `libvpx-vp9` (`-cpu-used 5 -deadline realtime`) and `libsvtav1` (`-preset 10`) needed fast presets — their defaults are tuned for quality, not CPU time, and would have made 84 encodes noticeably slower on a 3-second clip. With these, all 84 files finish in ~19s total (measured), well under the 10-minute local-compute budget.

## Phase 2 — actual GOP measurement confirms the h264/simulator caveat is real

- `src/pipeline/probe.py` measures *actual* keyframe interval (not the requested recipe value) by reading per-frame `key_frame` flags via ffprobe and averaging the gaps between keyframe indices. This directly validated the Phase 1 caveat: h264 hops (routed through Harsh's simulator, which has no GOP flag) show only 1 keyframe in a 90-frame clip and `actual_gop: None` (unmeasurable within the clip), while h265/vp9/av1 hops (direct ffmpeg, explicit `-g 60`) measure `actual_gop: 60.0` exactly. This is the concrete "actual vs. requested" evidence the phase's goal calls for.
- `router_target` is derived by parsing the last `__<codec>_G<depth>` tag out of the Phase 1 lineage-encoded filename, rather than threading extra state through from `build_chain_tree`. Files with no such tag (the original source) get `clean_G0`.
- All 85 rows (1 clean source + 84 transformed) share one source_id (`synthetic_test_input`) since they all derive from the single Phase 0 synthetic clip — clearly labeled as synthetic, matching rule 1. The splitter's ratio/leakage logic is tested separately against an explicitly-dummy multi-source fixture inside `tests/test_phase2.py`, never against real/production data, since one real source_id can't exercise a 70/15/15 split meaningfully.

## Phase 3 — real dataset acquisition (FF++ c23 + Celeb-DF v2)

- **Kaggle credentials:** user-provided API key + username, written to `~/.kaggle/kaggle.json` (chmod 600, outside the repo, never committed, never echoed in chat). Verified via a read-only `kaggle datasets list` call before any download was attempted.
- **Sample budget:** user approved 45 total videos (not the 80-120 default) — 25 from FF++ c23, 20 from Celeb-DF v2.
- **Exact composition (see `configs/dataset_sample.yaml`):** FF++ — 5 real identities (`000,001,002,004,005`) × {real clip + 4 manipulation methods: Deepfakes, Face2Face, FaceSwap, NeuralTextures}, using FF++'s official id-pairing (verified identical pairing reused across methods, e.g. `000_003.mp4` exists in every method folder). Celeb-DF v2 — 5 identities (`id0,id16,id17,id19,id20`) × {1 real clip + 3 confirmed synthesis clips}. Every file's `source_id` is its first identity number, so a real clip and all its fakes land in one group, per the spec's leakage requirement.
- **FF++ dataset structure, discovered via Kaggle API pagination + the dataset's own metadata description** (not guessed): `xdxd003/ff-c23` nests everything under a `FaceForensics++_C23/` root, with `original/` (1000 real) + 6 manipulation-method folders (1000 fakes each) + a `csv/` folder of per-method metadata. Confirmed via `kaggle datasets metadata` rather than blind pagination once the pattern was unclear.
- **Bug found and fixed — missing path prefix:** initial download attempt used paths without the `FaceForensics++_C23/` root (e.g. `original/000.mp4` instead of `FaceForensics++_C23/original/000.mp4`), causing all 25 FF++ downloads to 404. Fixed in `configs/dataset_sample.yaml`.
- **Bug found and fixed — filename collision:** all 4 manipulation methods for a given FF++ identity share the identical basename (e.g. `000_003.mp4` in both `Deepfakes/` and `Face2Face/`). Downloading all 4 into one flat directory silently overwrote 3 of every 4 (no error raised — the overwritten files just vanished). Fixed by downloading each method into its own subdirectory (`data_cache/raw/ffpp/<method>/`).
- **Bug found and fixed — zip-wrapped downloads:** Kaggle's `dataset_download_file` names the saved file after its signed download URL, not the requested path, and for some (not all, no clear pattern) files that URL ends in `.zip` — a real zip archive wrapping the single requested file, not a naming quirk. The original code only checked for the plain filename and logged false "[MISSING]" for every zip-wrapped file. Fixed by diffing the directory before/after each download call to find whatever actually landed, then auto-unzipping if needed (`src/data/download_sample.py::_download_one`).
- **Result:** all 45 files downloaded cleanly (72.1MB total, well under the ~150-250MB estimate), all verified playable via ffprobe, source_id groups confirmed correct size (5 FF++ ids × 5 files, 5 Celeb-DF ids × 4 files).
- **Full-chain-on-all-45 cost check:** timed the Phase 1 84-file transform chain on one real video (`ffpp/original/000.mp4`, 640x480, 15.8s) — 2m43s, ~92MB. Scaled to all 45 real sources: ~2 hours, ~4GB. This crosses BUILD.md's own stop-and-ask thresholds (>10 min, >1GB), so this was surfaced to the user as a separate decision rather than silently run. **User chose: smoke-test only** — the one real-video chain run above stands as proof the pipeline works on real (not synthetic) footage; the full 45-source manifest is probed and leakage-split at the clean/G0 level only (`data_cache/manifest/metadata_real.jsonl`, `src/data/build_real_manifest.py`), kept separate from Phase 2's synthetic `metadata.jsonl`. Bulk multi-generation transforms on real data are deferred to whenever they're actually needed (e.g. training-time augmentation), not pre-materialized now.
- **Bug found and fixed — shared chain directory:** Phase 2's `build_phase1_synthetic_manifest()` globbed *all* `.mp4` files in `data_cache/chains/` to assemble its 85-row synthetic manifest. Since the real-video smoke test above also wrote into that same shared directory, the glob picked up the real video's 84 files too (169 rows instead of 85), silently mixing real and synthetic rows into what's supposed to be a clearly-synthetic artifact — exactly what rule 1 warns against. Fixed by filtering the glob to the synthetic source's own filename prefix (`test_input__*.mp4`).

## Phase 4 — face detector: mediapipe over facenet-pytorch

- **Tried first:** `facenet-pytorch` (BUILD.md's first-listed option alongside mediapipe). `pip install facenet-pytorch` failed outright — its `setup.py` throws `KeyError: '__version__'` under current pip/setuptools, an upstream packaging bug unrelated to this environment (the package is largely unmaintained).
- **Used instead: mediapipe.** Installed cleanly (prebuilt wheel, no compilation). Its old `mp.solutions.face_detection` API was removed in the installed version (1.1.1); used the current Tasks API (`mediapipe.tasks.python.vision.FaceDetector`) instead, which needs a separate model file.
- **Model download:** `blaze_face_short_range.tflite` (float16, 229KB — well under the 50MB checkpoint threshold), fetched from the official Google-hosted URL confirmed via `developers.google.com/edge/mediapipe/solutions/vision/face_detector` (not guessed from memory). Stored at `data_cache/models/` (gitignored, like all data_cache contents).
- **Alignment design:** detected bbox is expanded to a square (`scale=1.3`) centered on the box, clamped to image bounds, then resized to 224x224 — same "expand box, preserve center, clamp to bounds" pattern used elsewhere in this project (Phase 1's "never upscale" scale filter). Frames where no face is detected fall back to a center-square crop of the whole frame rather than raising, so one bad frame doesn't crash preprocessing of an otherwise-good clip; tested explicitly in `tests/test_phase4.py`.
- **DCT:** luma via standard BT.601 weights (0.299/0.587/0.114), per-8x8-block 2D DCT-II via `cv2.dct`, row-major block order. Verified correct on a synthetic flat-color input (energy only in the DC coefficient, confirming no cross-block leakage or ordering bug).
- **Visual proof:** `reports/phase4_samples/face_crop_grid.png` (3 real files x 8 frames, including a real/deepfake pair of the *same* identity -- `ffpp/original/000.mp4` vs `ffpp/deepfakes/000_003.mp4` -- visibly showing manipulation artifacts around the mouth) and `dct_heatmap.png` (mean DCT energy per block, showing a clear face-shaped low-energy silhouette against higher-energy background/edges -- a sanity check that the DCT features are spatially meaningful, not noise).

## Phase 5 — architecture scaffold

- **DINOv2 pretrained weights (~330MB+): deferred to Phase 7, not downloaded here.** Asked the user explicitly (crosses the project's own 50MB auto-download threshold). User chose random-init-for-now. The spatial branch is built at ViT-B/14's exact dimensions (embed_dim=768, patch=14, depth=12, heads=12) so it's a drop-in shape match for real pretrained weights later; only the *values* are random, logged clearly at construction time (`SpatialBranch: using a randomly-initialized ViT-B/14-shaped backbone...`).
- **Custom ViT with separate q/k/v projections, not a fused qkv matrix.** DINOv2's official checkpoint (and most ViT implementations) use one fused `qkv: Linear(768, 2304)` for efficiency. Building a custom attention module with separate `q_proj`/`k_proj`/`v_proj` instead makes "LoRA on q and v only" a clean, direct attachment (`LoRALinear` wraps exactly those two) rather than requiring slicing into a fused weight matrix. Trade-off: real pretrained DINOv2 weights can't be loaded into this module's state_dict as-is -- whoever does the Phase 7 pretrained-weight integration will need to either split the fused qkv checkpoint on load, or adapt this module to a fused qkv + rank-8 adapters on the q/v slices. Noted here so it isn't a surprise later.
- **LoRA design:** `LoRALinear` wraps a frozen base `nn.Linear`; only the rank-8 low-rank A/B matrices are trainable (`B` initialized to zero, so the adapter starts as a no-op, standard LoRA practice). This freeze-base/train-adapter wiring is correct regardless of whether the base weights end up random (now) or pretrained (Phase 7) -- it's how LoRA fine-tuning is meant to work either way.
- **Frame aggregation split across two modules:** `fusion.py` does cross-attention + pools over the 256 RGB query positions to one z per *frame* (matches its stated job, "pooled to z ∈ R^768"); `model.py` then mean-pools over the 16 *frames* to one z per *video* before routing. Keeping these separate makes each module's job legible on its own.
- **Verified:** dummy batch (B=2, F=4) through the full forward pass -- all shapes correct at every stage (spatial, frequency, fusion, full model), exactly top-2 gate weights nonzero per sample (summing to 1), a single `.backward()` call produces finite gradients on all 103.7M trainable parameters (118.6M total, the rest frozen backbone). `reports/architecture_summary.txt` has the per-module breakdown.
- **Not addressed:** BUILD.md's Phase 5 deliverable mentions "the HTML architecture diagram (already built)" as a visual explainer alongside the parameter summary. No such diagram exists in this repo -- it's referenced as already existing somewhere outside Claude Code's working scope (report/presentation materials). Flagged here rather than fabricated; worth pulling in during Phase 10 if the user has it.

## Phase 6 — loss functions

- **Router changed to return a dict, not a tensor.** `L_route` needs raw pre-softmax logits and `L_bal` needs the raw pre-top-k softmax distribution, neither of which the Phase 5 `gate_weights` (post-top-k, renormalized) can reconstruct. `Router.forward()` now returns `{"gate_weights", "probs", "logits"}`; `model.py`'s output dict gained `router_probs`/`router_logits` alongside the existing keys. Checked this didn't break Phase 5's tests (none called `Router` directly, only through the full model) before proceeding.
- **`L_route` cluster mapping (`configs/model.yaml`'s `router_clusters`):** explicit 5-entry mapping matching Appendix A's "clean + 2 codecs x 2 depths" scheme exactly (`clean_G0`->0, `h264_G1`->1, `h264_G2`->2, `h265_G1`->3, `h265_G2`->4). Anything else (G3 at any codec, vp9/av1 at any depth) falls back to a `default` entry (cluster 0) purely so the loss stays well-defined if such data ever reaches it -- a real training run at this project's scale should only use data whose router_target is one of the 5 explicit entries, not rely on the fallback as a real cluster assignment.
- **Bug found and fixed: `-inf * 0 = NaN` in `L_con`.** The self-similarity position is masked to `-inf` before `logsumexp`; multiplying that `-inf` by the (False-valued) self-exclusion mask produced `NaN` instead of `0` under IEEE float rules, corrupting every row's loss. Fixed by zeroing those positions in `log_prob` before the mask-multiply, not after.
- **`L_con` sanity-checked correctly (after fixing an initially-flawed manual test):** same-source-identical-and-well-separated-from-other-sources gives loss ≈ 0 (9.5e-7); same-source-forced-orthogonal-while-coincidentally-aligned-with-a-different-source gives loss = 14.3. (First manual check collapsed all 4 dummy vectors to be identical, which tests nothing -- caught before it became a bogus test.)
- **5-dummy-optimizer-steps test uses BUILD.md's actual Phase 7 hyperparameters (lr=1e-4, wd=0.05), not an arbitrary test-only value.** An initial attempt at lr=1e-3 diverged (loss rose from 1.93 to 3.70 over 5 steps) on this random-init, random-data setup; lr=1e-4 converges cleanly (1.93 -> 1.46). Using the real training config here is both more meaningful and avoids tuning a throwaway number.
- **`L_bal`:** standard Switch Transformer load-balancing loss (`K * sum_k f_k * P_k`), computed on the router's raw pre-top-k softmax, consistent with the original formulation (hard top-1 assignment for `f_k`, soft probability mass for `P_k`).

## Phase 7 — training loop

- **Real bottleneck found: full-scale model is ~140s/step on CPU** (measured directly: 72s forward + 67s backward at B=4, F=16 -- 12-layer ViT-B/14 + 4-layer/784-token frequency transformer + cross-attention fusion, all applied to B*F=64 per-frame sequences). Five steps at that scale would be ~12 minutes, over this project's own 10-minute local-compute budget. This is additional concrete evidence for BUILD.md's own pre-established call that real training needs Kaggle, not this M2 Mac.
- **Local dry-run uses a reduced `n_frames` (4, via `n_frames_override`), not the production value (16).** Matches the precedent already set in Phase 5/6 (small dummy batch shapes to keep CPU tests cheap) -- the dry-run's job is proving the loop doesn't crash, not running at realistic scale. 5 steps at n_frames=4 took ~100s; the pytest version uses n_frames=2 with 2 steps (~11s) to keep routine test runs fast. `n_frames_override=None` uses the real config -- that's what `notebooks/train_kaggle.py` passes.
- **Checkpoint size:** saving full AdamW optimizer state (2 extra moment buffers per trainable param) produced a 1.3GB checkpoint for this architecture -- over the project's 1GB-file threshold. `save_optimizer_state` is now an explicit flag (default off for the dry run, since there's nothing meaningful to resume; on for real Kaggle checkpoints where resuming across Kaggle's ~9-12hr session limit matters). Without it: 452MB.
- **Experiment tracking: local CSV logging only, no W&B.** BUILD.md explicitly says ask, don't assume. Defaulted to local-only (avoids needing a new credential) since the user's "build all phases now" instruction meant proceeding without a dedicated round-trip for this specific sub-decision -- flagged here and in the final summary; say the word if W&B should be wired in instead.
- **Kaggle handoff (`notebooks/train_kaggle.py`): a thin wrapper around the same `src/train/train.py` used locally, not a separate reimplementation** -- just `device="cuda"`, the real `n_frames`, a larger batch, and periodic checkpointing. `train()` gained `device`, `checkpoint_every`, and `resume_from` params to support this without duplicating the training loop. The script expects the user to upload `src/`, `configs/`, and the relevant `data_cache/` subdirs as a Kaggle Dataset (not re-fetch FF++/Celeb-DF from Kaggle's hosted copies) -- this reuses 100% of the already-tested local manifest/path logic as-is, rather than writing Kaggle-specific path-remapping code.
- **Checkpoint placement after a real Kaggle run:** default expected location is `data_cache/checkpoints/checkpoint.pt` (same directory the dry-run checkpoint already lives in) -- stated as the default in the script's setup instructions rather than left for a later interactive question, since BUILD.md's own question here ("ask where to place it") only has one sensible answer given the directory already established by the dry run.
- Claude Code cannot execute Kaggle notebooks itself (confirmed limitation, not a policy choice) -- this phase's Claude-Code-side work ends at a proven-correct local dry-run + a ready-to-run script, matching BUILD.md's own framing of Phase 7's deliverable ("plus (once the user runs it) a real checkpoint... from Kaggle").

## Phase 8 — evaluation / robustness benchmark

- **No real checkpoint exists, so this is entirely the synthetic-sanity-check branch BUILD.md explicitly allows** -- the Phase 7 dry-run checkpoint has random weights (never real training), and no Kaggle run has happened yet. Every output is prominently watermarked: filenames prefixed `SYNTHETIC_`, the chart's title in red reads "SYNTHETIC sanity check -- NOT real results", the table's header says the same. This isn't decoration -- it's rule 1 (never present synthetic numbers as real) made hard to miss even by someone skimming `reports/` without reading `DECISIONS.md`.
- **"Seen vs unseen chain" slicing definition:** BUILD.md references "the held-out-chain list from the spec" without enumerating it in BUILD.md itself (it points at a fuller external spec document not available here). Rather than invent an unrelated list, "seen" = the same 5 router_targets already explicit in `configs/model.yaml`'s `router_clusters` (clean_G0 + the reduced 2-codec x 2-depth set this project's scale actually trains on, per Appendix A). "Unseen" = everything else (deeper hops, vp9/av1). This keeps the seen/unseen story consistent with the router's own reduced-cluster design from Phase 6, rather than introducing a second, disconnected definition of "what the model has seen."
- **Ablation variants are evaluated via a `pred_<variant>` column per row, not by actually training 3 separate models.** Real ablation training (MoE vs single-head vs no-L_con) would need 3x real Kaggle training runs -- out of scope for what's achievable right now. The comparison *harness* (slicing, metrics, table, chart) is fully built and tested; it's ready to consume real per-variant predictions the moment real checkpoints exist for each variant.
- **Synthetic predictions use a deliberately-designed depth-dependent "skill" curve** (MoE degrading more gracefully than single-head, which degrades more gracefully than no-L_con, as depth increases) so the demo chart has the shape the architecture doc's "AUC vs depth" story describes. This is illustrative of what the comparison *should* show if the design works, not a claim that it does -- clearly labeled as such everywhere it appears.
- **Bug found and fixed:** the benchmark table's text formatting used a column width (10) narrower than the `"seen_unseen"` slice-type string (11 chars), causing it to run into the adjacent `key` column (e.g. `seen_unseenseen` instead of two separate columns). Caught by reading the actual generated file rather than just checking it existed.
