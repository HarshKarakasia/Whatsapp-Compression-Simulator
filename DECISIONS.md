# Decisions

## Phase 0 — Harsh's WhatsApp Compression Simulator

- **Tested on:** 2026-10-17, using the synthetic `test_input.mp4` from Phase 0 (ffmpeg `testsrc` + `sine`, 320x240, 15fps, 3s, no real footage).
- **Repo:** `https://github.com/HarshKarakasia/Whatsapp-Compression-Simulator`, cloned into `external/whatsapp-compression-simulator/`.
- **Scriptable, no GUI:** confirmed. `compress.py` is a pure CLI (`argparse`), video-in/video-out, with `--dry-run`, `--batch`, and single-file modes. No GUI dependency. Detects `ffmpeg`/`ffprobe` via `shutil.which()` first (Windows registry paths are a fallback only), so it works unmodified on macOS once ffmpeg is on `PATH`.
- **Exposes real parameters, not a black box:** confirmed. Every run writes a JSON sidecar (`output/simulated/<stem>_simulated.json`) containing the exact encoder (`libx264`), CRF (28), preset (`medium`), pixel format (`yuv420p`), max resolution box (1280x720), audio codec/bitrate, the full `ffmpeg` argv list, and the exact command string. Ran `--dry-run` first to preview the command, then a real run — both matched exactly.
- **Runs cleanly, no manual intervention:** confirmed. `python3 compress.py input/test_input.mp4` succeeded in 0.09s on the first try, output file is a valid playable MP4 (`ffprobe` confirms `h264`/`aac` streams).
- **Decision: integrate it as the "WhatsApp hop" implementation inside `src/pipeline/`** (wrap, don't fork-and-edit). Its CLI contract (`compress.py <input> [--crf --max-width --max-height --preset --fps]`, JSON sidecar with `parameters` + `ffmpeg_command_args`) is stable enough to shell out to directly, and its sidecar's `parameters`/`ffmpeg_command_args` double as the actual-vs-requested metadata Phase 2 needs anyway. `compare.py`'s ffprobe-based metadata/comparison pipeline will **not** be reused — Phase 2 already specs its own `src/pipeline/probe.py`, and duplicating that logic would just be two sources of truth for the same ffprobe fields.
- **Caveat:** the simulator's baseline profile (CRF 28, max 1280x720, `medium` preset) is a *single* fixed recipe calibrated for one WhatsApp hop. Phase 1's multi-codec, multi-generation chain (H.264/H.265/VP9/AV1 × 3 depths, per `configs/transform.yaml`) needs its own recipe table regardless — this simulator covers one point in that space (H.264 generation-1-ish), not the whole tree. It will be wrapped as one named recipe/codec option, not treated as the full Phase 1 pipeline.

## Phase 0 — ffmpeg toolchain

- **Tested on:** 2026-10-17.
- **Problem:** `brew install ffmpeg` on this machine could not fetch pre-built bottles (bottle host unreachable in this sandboxed environment) and fell back to compiling ffmpeg + all codec deps (x264, x265, aom, dav1d, svt-av1, ninja as a build-tool dependency) from source. Verified via `ps aux` mid-install: it was still building `ninja` itself ~5 minutes in, before even reaching `x265`/`ffmpeg`. Estimated 15-20+ minutes remaining.
- **Decision:** killed the brew build. Used a dedicated conda-forge environment instead (`conda create -n fyp-ffmpeg -c conda-forge ffmpeg`), which installed in under a minute and provided ffmpeg 9.0.2 with the full codec set this project needs: `libx264`, `libx265`, `libvpx-vp9`, `libsvtav1`.
- **Caveat:** the base conda environment's `ffmpeg` (an older, codec-incomplete 4.3.2 build pulled in as a side effect of testing conda-forge) sits earlier on `$PATH` than both Homebrew and the new env, and `conda remove` refused to uninstall it cleanly (unrelated `requests`-is-a-conda-dependency conflict). Rather than fight global `$PATH` order or force-remove conda package files, `configs/paths.yaml` pins the correct binaries by absolute path (`ffmpeg_binary` / `ffprobe_binary`), and all project code must resolve ffmpeg through that config value, not through `$PATH` lookup. This is also just more reproducible than relying on shell PATH order across machines.

## Phase 1 — Transform chain scaling filter and rate control

- **Scaling:** all four codecs use the same "max box, never upscale, preserve aspect, even dims" scale filter as Harsh's simulator (`scale=w='min(iw,W)':h='min(ih,H)':force_original_aspect_ratio=decrease,...`), rather than forcing an exact target height. On the tiny 320x240 synthetic clip this means resolution stays unchanged through the whole chain (it's already below every hop's box) — expected and fine for a synthetic mechanics test; on real FF++/Celeb-DF source footage (720p+) this will actually downscale through the ladder as the spec intends.
- **Rate control bug found and fixed:** `libsvtav1` rejects `-maxrate`/`-bufsize` outside CRF mode (`Max Bitrate only supported with CRF mode`), which broke every AV1 hop whose input was itself a prior generation. Fixed via a per-codec `supports_maxrate_bufsize` flag in `configs/transform.yaml` — AV1 gets `-b:v` alone (VBR target, no hard ceiling); h264/h265/vp9 keep the tight VBV cap (`-maxrate`/`-bufsize` = target bitrate).
- **Audio:** the whatsapp-simulator-wrapped h264 hop keeps AAC audio (no CLI flag to disable it short of the source having none); the three direct-ffmpeg hops (h265/vp9/av1) drop audio via `-an` for simplicity and because muxing video-only VP9/AV1 into `.mp4` is more reliably supported than audio+VP9/AV1 combinations across ffmpeg builds. This means audio presence varies by lineage — harmless for Phase 1's mechanical tests, worth knowing before Phase 4 preprocessing (which only reads video frames anyway).
- **Encoder speed:** `libvpx-vp9` (`-cpu-used 5 -deadline realtime`) and `libsvtav1` (`-preset 10`) needed fast presets — their defaults are tuned for quality, not CPU time, and would have made 84 encodes noticeably slower on a 3-second clip. With these, all 84 files finish in ~19s total (measured), well under the 10-minute local-compute budget.
